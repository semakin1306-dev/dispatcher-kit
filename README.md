# Диспетчерская

Инструмент, который ведёт параллельную работу нескольких агентов (Claude Code или Codex CLI) над одним git-репозиторием. Каждая задача получает свою рабочую копию, свои проверки и свою очередь на влив; человек видит всё на одной странице и решает, что вливать и что выкатывать.

Для кого: для разработчика или небольшой команды, у которых агенты уже пишут код, и хочется вести сразу несколько задач без путаницы в ветках, папках и прогонах тестов. Подходит любой стек: диспетчерская запускает ваши команды и ничего не знает о языке проекта.

Сама диспетчерская — Node 22+ без зависимостей: ни `package.json`, ни `npm install`. Всё, что она знает о вашем проекте, лежит в одном файле `dispatcher.project.json`, который собирается при первой настройке.

## Словарь

| Слово | Что значит |
|---|---|
| **Эпик** | Пачка связанных задач с общей целью. У эпика своя ветка и папка оркестратора, свои слоты и поезда. |
| **Волна** | Одна задача эпика с номером `WV-NNNN`. У волны ветка `dev/wv-NNNN-…`, план и строка `Wave: WV-NNNN` в каждом коммите. |
| **Слот** | Рабочее место волны: отдельная рабочая копия (git worktree) рядом с проектом, свой агент, свои запреты на правку. |
| **Поезд** | Слот области проекта, через который по очереди проходят несколько волн — **вагонов**. Нужен, когда задачи одной области лучше вливать друг за другом. |
| **Станция** | Шаг пути волны: план → красный тест → код → сборка → гарды → тесты → ревью → регресс → коммит → в staging → на стенде → приёмка → в проде. Большинство отметок ставится само по git и прогонам; станции выключенных модулей не показываются. |
| **Область** | Часть репозитория (`areas` в конфиге): свои пути, свои задачи проверок. Слоты разных областей не мешают друг другу. |
| **Задача** | Команда проверки из конфига (`tasks`): тесты, линтер, типы, сборка. Запускает её диспетчерская, а не агент. Задача с `gate: true` — **гард**: без него волна не вливается. |
| **Оркестратор** | Агент эпика. Пишет планы волн, заводит слоты, отвечает инженерам слотов, следит за порядком вливов. Работает в своей папке. |
| **Инженер слота** | Агент одной волны. Пишет код и тесты в своём слоте и докладывает оркестратору в строгом формате. |
| **Ревьюер** | Разовый агент, который читает правку слота перед вливом и выносит вердикт: ЗА, ВОПРОСЫ или ПРОТИВ. Только читает. |

Внутри диспетчерская зовёт интеграционную ветку вашего проекта `staging`, а прод-ветку — `main`, как бы они ни назывались у вас: настройка создаёт локальные ветки с этими именами, которые отслеживают ваши.

## Что потребуется

- **Node.js 22** или новее.
- **git 2.31** или новее.
- **Агент в PATH**: `claude` (Claude Code) или `codex` (Codex CLI). Если агент установлен не в PATH — путь к нему пишется в ключ `agent.bin` конфига: полный, `~/…` (от домашней папки) или относительный (от папки конфига); голое имя ищется в PATH.
- Проект — git-репозиторий с remote.
- На Windows — Git Bash: через него идут задачи с вводом, у которых команда — пускатель `.cmd` (`npx`, `npm`), и команды служб для тестов (`machines.*.services`).

## Как начать

1. Клонируйте репозиторий **рядом** с проектом, не внутрь него:

   ```
   ~/code/demo-shop          ← ваш проект
   ~/code/dispatcher-kit     ← диспетчерская
   ~/code/demo-shop-wt       ← рабочие копии слотов (создаст диспетчерская)
   ```

2. Откройте папку диспетчерской в Claude Code или Codex. Агент прочитает `CLAUDE.md` / `AGENTS.md`, увидит, что `dispatcher.project.json` ещё нет, и проведёт настройку по [SETUP.md](SETUP.md): сам определит стек, области, ветки и CI, спросит то, что по коду не узнать, покажет итог и после вашего согласия запишет конфиг.
3. Проверка установки — `node setup.mjs doctor`. Он же печатает, какие модули включены и почему остальные выключены.
4. Запустите страницу (раздел «Страница и тесты» ниже) и заведите первый эпик: в окне оркестратора — навык `/new-epic`, или командой `node scripts/dev/epic.mjs new --id <id> --title "<название>"`.

Настройка ничего не коммитит и не пушит. В проекте она создаёт только две локальные ветки-роли — и только с вашего согласия.

## Своё и общее: правило обновлений

Своё у вашей установки живёт только здесь:

- `dispatcher.project.json` — конфиг проекта;
- `dispatcher.project.mjs` — необязательная код-надстройка: то, что не выразить конфигом. Список функций закрытый: `buildSteps`, `slotPrepare`, `remoteCmd`, `parseOutput` (описания — в [рецептах](docs/recipes/README.md));
- папка `project/` — ответы настройки и всё прочее своё.

Все три закрыты `.gitignore`. Код диспетчерской под проект не правится — поэтому её можно обновлять обычным `git pull`. После обновления — `node setup.mjs doctor`.

## Модули

Необязательные части включаются ключом `modules` в `dispatcher.project.json`. Выключенный модуль не стартует, его маршруты отвечают 404, его панели на странице нет. Модуль, включённый в конфиге, но без нужных ключей, не заработает — `doctor` скажет, чего не хватает.

| Модуль | Что делает | По умолчанию | Что нужно |
|---|---|---|---|
| `review` | Независимое ревью: разовый агент-ревьюер читает правку слота перед вливом. | вкл | — |
| `backlog` | Бэклог: карточки идей и находок вне текущего эпика и их разбор. | вкл | — |
| `retro` | Ретро эпика: после закрытия эпика разовый агент разбирает журнал событий и предлагает правки процесса карточками бэклога. | выкл | модуль `backlog` |
| `machines` | Машины прогонов: проверки идут и на других машинах по ssh, код доставляется по sha. | выкл | в `machines` хотя бы одна машина с `ssh` |
| `release` | Выкат стенда и прода командами из конфига; влив `staging → main` — только кнопкой человека. | выкл | `release.stand.run`, `release.prod.run` или `release.prod.pushDeploys` |
| `accept` | Приёмка на стенде: агент слота пишет чек-лист, прогон — командой из конфига, вердикт ставит человек. | выкл | `accept.run` |
| `tg` | Телеграм-бот: вопросы агентов приходят в Телеграм с кнопками вариантов. | выкл | свой бот, токен через `node scripts/dev/tg-setup.mjs` |
| `win-desktop` | Рабочий стол Windows: монитор машины, раскладка окон по слотам, ярлыки запуска. | выкл | только Windows |

Каталог модулей — `scripts/dev/modules-catalog.mjs`. Стартовая настройка проставляет `modules` по вашим ответам.

### Переключатели поведения

Второй уровень — `settings.json` в папке данных (по умолчанию `<папка слотов>/_dashboard`). Это поведение на ходу; меняется со страницы настроек.

| Переключатель | Что делает | По умолчанию |
|---|---|---|
| `autoCommit` | Коммит слота ставится сам, когда ревью пройдено, а в слоте есть незакоммиченное. | выкл |
| `autoMerge` | Влив в staging сам, когда проверки и ревью зелёные. | выкл |
| `autoTrain` | Автопоезд: после прогона следующая станция слота запускается сама. | выкл |
| `autoSyncConflict` | Если ветка слота конфликтует с ушедшим вперёд staging, подтягивание staging в слот запускается само. | выкл |
| `selfCommit` | Когда агент слота коммитит сам: `word` — только по слову человека, `station` — после каждой станции плана. | `word` |
| `fullPermissions` | Агентам — полные разрешения без вопросов. | выкл |
| `autoResults` | Итоги прогонов сами уходят агенту слота. | вкл |
| `retroAuto` | Ретро запускается само после закрытия эпика (при модуле `retro`). | выкл |
| `tgBot` | Бот в Телеграме работает (при модуле `tg`). | выкл |
| `commitTrailer` | Строка-подпись коммитов, сделанных со страницы. | пусто |

Ответ настройки об автономии задаёт стартовый набор: `manual` — всё выключено, `commit` — включён автокоммит и `selfCommit: station`, `merge` — ещё и автовлив, автопоезд и разбор конфликтов.

## Безопасные умолчания

- Автономия по умолчанию — `manual`: коммит и влив в staging делаются кнопкой человека.
- Выкат стенда и прода, пуш в прод-ветку, сброс ветки слота и «принудительно» — только человек, в любом режиме автономии. Ответ из Телеграм-бота даёт право только на ответ, коммит и влив в staging.
- Если пуш в прод-ветку сам выкатывает прод (`release.prod.pushDeploys`), диспетчерская показывает пуш как выкат.
- Агенту слота закрыты пуш, перезапись истории, переключение веток, `git add -A`, `ssh`/`scp` и чтение `.env`; коммит он спрашивает. Свои запреты добавляются в `deny` и `areas.*.denyEdit`.
- Бот и полные разрешения агентов выключены.
- Сервер слушает только `127.0.0.1`.

## Codex — экспериментально

Адаптер Codex CLI (`scripts/dev/runtimes/codex.mjs`) написан по документации и **вживую не проверялся**: автор диспетчерской пользуется только Claude Code. Проверен он контрактным тестом на поддельном бинарнике.

Как подключить:

1. Поставить Codex CLI (`npm install -g @openai/codex`) и войти: `codex login`.
2. В `dispatcher.project.json` — `agent.runtime: "codex"`; если `codex` не в PATH — путь в `agent.bin`.
3. Модели ролей — `agent.models` (`orch`, `slot`, `review`; пусто — модель Codex по умолчанию).
4. Сеть из песочницы выключена; включает её `agent.network: true`.
5. Навыки диспетчерской `node setup.mjs apply` кладёт в `~/.agents/skills`.
6. Проверить: `node setup.mjs doctor` — в строке «Агент» видны путь и версия `codex`.

Известные ограничения:

- Запреты слота держатся в основном текстом `AGENTS.override.md`: песочница `workspace-write` реально закрывает только запись вне папки слота и выход в сеть.
- Коммит силами агента может не пройти: папка git рабочей копии лежит вне песочницы. Коммит — кнопкой.
- Счётчик контекста — 0 (`ctxTokens`), поэтому ротация оркестратора по токенам не срабатывает.
- Нет постоянного процесса: каждый ход — отдельный запуск `codex exec --json`, продолжение — через `resume`. Нет потока текста по мере ответа и нет запросов разрешений на инструмент. На Windows прерывание хода — снятие процесса.

Обходов для этих ограничений нет — пробуйте свои. Заработало, нашли ошибку или доделали — присылайте pull request. Подробнее — [рецепт про Codex](docs/recipes/codex.md).

## Страница и тесты

Сервер со страницей:

```
node scripts/dev/dashboard/server.mjs
```

Страница — `http://127.0.0.1:4777`. Порт — переменная `DASH_PORT`, своя папка данных — `DASH_DATA`, другой конфиг — `DISPATCHER_PROJECT`. Безопасный перезапуск (дождаться, пока прогоны закончатся) — `node tools/restart-dashboard.mjs`. На Windows с модулем `win-desktop` есть пускатели `desktop/start-dispatcher.bat` и `desktop/stop-dispatcher.bat`.

Тесты диспетчерской — из корня:

```
node --test
```

Тесты идут на демо-конфиге `test/fixtures/project.demo.json` и не трогают ваш проект. Перед публикацией своих правок в диспетчерскую — ворота `node tools/publish-check.mjs`: они ищут адреса, личные пути, почту и ключи.
