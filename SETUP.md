# Настройка диспетчерской под проект

Этот файл — порядок действий для агента (Claude Code, Codex CLI или другого), который открыл папку диспетчерской впервые. Человек может читать его вместе с агентом: здесь же сказано, что и зачем у него спросят.

Диспетчерская ведёт параллельную работу агентов над одним репозиторием: каждая задача получает свою рабочую копию (слот), свои проверки и свою очередь на влив. Чтобы она работала с вашим проектом, ей нужно знать, где он лежит, как делится на части, чем проверяется, на каких машинах и что можно делать без человека. Всё это записывается в один файл — `dispatcher.project.json`.

## Что произойдёт

1. Агент прочитает проект и сам определит, что сможет: стек, области, ветки, CI, память машины.
2. Спросит у человека остальное — решения, которые по коду не узнать.
3. Соберёт конфиг, покажет его и после согласия запишет.
4. Проверит установку и доведёт её до зелёного состояния.

Настройка ничего не коммитит и не пушит. В проект она пишет только одно: две локальные ветки-роли (шаг 5), и только с согласия человека.

## Порядок действий

### 1. Узнать, где проект

Диспетчерская лежит отдельной папкой **рядом** с проектом, не внутри него. Если путь к проекту не назван — спроси. Дальше `<проект>` — этот путь.

### 2. Определить, что видно без вопросов

```
node setup.mjs detect --repo <проект> --json
```

Команда только читает. В ответе:

- `known` — что определилось уверенно (название, ветки, CI, число воркеров);
- `ask` — что нужно спросить: у каждого вопроса есть `text`, `why` (на что влияет ответ), `type`, иногда `options`, `suggested` (предложение) и `suggestedWhy` (откуда оно);
- `facts` — сырые факты, по которым строились предложения.

Если `facts.git.isRepo` ложно — остановись и скажи человеку: диспетчерская работает только с git-репозиторием.

### 3. Показать найденное и задать вопросы

Сначала коротко, одним списком, покажи `known` и спроси, всё ли верно. Потом иди по `ask`.

Правила разговора:

- **Спрашивай блоками**, по полю `block`, а не всё разом. Если у тебя есть инструмент для вопросов с вариантами — пользуйся им; если нет — спрашивай обычным сообщением.
- **Объясняй, на что влияет ответ** — это поле `why`. Формулировку можно менять, смысл нельзя.
- **Предложение показывай как вариант по умолчанию**, вместе с тем, откуда оно взялось.
- **Вопрос с `dependsOn` задавай, только если ответ на родительский вопрос непустой.** Нет стенда — не спрашивай его адрес.
- **Сложные ответы показывай человеческим языком.** Области, задачи, шаги подготовки и запреты приходят объектами — покажи их таблицей или списком, а не JSON, и спроси, что поправить.
- **Сначала прочитай сам, потом спрашивай.** Если ответ можно уточнить чтением (`package.json`, файлы CI, скрипты выката) — уточни и предложи уже проверенный вариант.
- **Не отвечай за человека.** Если он не знает или ему всё равно — оставь предложение и скажи, что оставил. Выдуманный ответ хуже пустого.
- **Не настаивай на автономии.** Режим `manual` — разумное начало; автокоммит и автовлив включаются позже одной настройкой.

Четыре ответа определяют почти всё остальное — на них не экономь:

| Вопрос | Почему важен |
|---|---|
| `git.integration`, `git.production` | От интеграционной ветки режутся слоты, в неё вливаются волны. Диспетчерская зовёт эти ветки у себя `staging` и `main`, как бы они ни назывались в проекте. |
| `git.pushDeploys` | Если пуш в прод-ветку сам выкатывает прод, диспетчерская обращается с пушем как с выкатом. |
| `areas` | Области — это то, что позволяет двум агентам работать одновременно и не столкнуться. |
| `tasks` | Задачи запускает диспетчерская, а не агент. Задача с `gate: true` — гард: без него волна не вливается. |

### 4. Записать ответы и посмотреть, что получится

Ответы — один JSON-файл: ключ — `id` вопроса, значение — ответ. Положи его в `project/answers.draft.json` (папка `project/` вне git).

```json
{
  "git.pushDeploys": true,
  "autonomy": "manual",
  "modules.tg": false,
  "machines.remote": [],
  "stand.run": ""
}
```

Сначала сухой прогон — он ничего не пишет:

```
node setup.mjs apply --repo <проект> --answers project/answers.draft.json --dry-run
```

Если команда отказала с «нет ответов на вопросы: …» — эти вопросы положено задать человеку, а не закрыть предложением. Задай их. Флаг `--accept-suggested` существует, но без человека его не ставь.

Покажи человеку итог своими словами: ветки, области, задачи и гарды, машины, режим автономии, включённые модули.

### 5. Применить

Скажи человеку, что будет записано, и после согласия:

```
node setup.mjs apply --repo <проект> --answers project/answers.draft.json --branches
```

Что запишется:

- `dispatcher.project.json` в папке диспетчерской — конфиг проекта;
- `project/answers.json` рядом с конфигом — ответы человека, чтобы повторная настройка не переспрашивала;
- `settings.json` в папке данных — стартовые переключатели по ответу об автономии (если файла ещё нет);
- навыки агента (`skills/*/SKILL.md`) — в профиль пользователя, туда, где их ищет выбранный рантайм: Claude Code — `~/.claude/skills/<имя>/`, Codex — `~/.agents/skills/<имя>/` (свой каталог — переменная `DISPATCHER_SKILLS_DIR`). В текстах навыков заглушка `<дом диспетчерской>` заменяется настоящим путём к этой папке. Чужой навык с тем же именем не перезаписывается — `apply` назовёт его. В папку проекта навыки не кладутся: агенты работают в рабочих копиях слотов, и навыки пришлось бы держать в git проекта;
- с флагом `--branches` — локальные ветки `staging` и `main` в проекте, которые отслеживают его интеграционную и прод-ветку. Рабочую папку проекта и удалённый репозиторий это не трогает.

Если у проекта уже есть своя ветка `staging` или `main` с другим смыслом, настройка её не тронет и сообщит об этом. В первой редакции эти два имени заняты диспетчерской — это известное ограничение; решение принимает человек (переименовать свою ветку или выбрать её же интеграционной).

### 6. Проверить

```
node setup.mjs doctor
```

Чини ошибки, пока не станет зелёным: у каждой есть строка «→ что сделать». Если в конфиге есть удалённые машины — `node setup.mjs doctor --net` проверит до них ssh.

В конце отчёта — таблица модулей: что включено, что выключено и почему.

### 7. Чего не выразить конфигом

Сборка, которая зависит от того, какие файлы менялись; особая подготовка слота; своя команда прогона на удалённой машине; свой разбор вывода тестов — всё это пишется функциями в одном необязательном файле `dispatcher.project.mjs` рядом с конфигом. Список функций закрытый: `buildSteps`, `slotPrepare`, `remoteCmd`, `parseOutput`. Описания — в `docs/recipes/`.

Правило: своё у проекта живёт только в `dispatcher.project.json`, `dispatcher.project.mjs` и папке `project/`. Код диспетчерской под проект не правится — тогда её можно обновлять обычным `git pull`.

## Повторная настройка

Запусти те же шаги ещё раз. Прежние ответы подставятся сами, `detect` покажет только новые вопросы. Перезаписать конфиг — `apply … --force` (прежний сохранится рядом как `dispatcher.project.json.prev`). Начать с чистого листа — `detect --fresh`.

## Справка по командам

| Команда | Что делает | Пишет? |
|---|---|---|
| `node setup.mjs detect --repo <проект> [--json] [--fresh]` | Определяет факты и план вопросов | нет |
| `node setup.mjs apply --repo <проект> --answers <файл> [--dry-run] [--force] [--branches]` | Собирает конфиг из ответов | да, перечисляет что |
| `node setup.mjs doctor [--net] [--json]` | Проверяет установку | нет |
