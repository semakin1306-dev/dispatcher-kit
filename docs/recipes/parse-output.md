# Свой разбор вывода тестов

## Когда нужен

Диспетчерская читает вывод задачи, чтобы знать, какие спеки (файлы тестов, пакеты) прошли и какие упали. На этом держатся регресс по тронутым путям, карантин нестабильных спек, перепрогон только упавших и выжимки падений для агента. Если раннер тестов не из заготовок или печатает необычно — нужен свой разбор.

Без разбора задача работает по коду возврата (`exit-code`): прогон зелёный или красный, и всё, что опирается на имена спек, для неё выключается само.

## Заготовки

Поле `parser` задачи — имя заготовки:

| Заготовка | Что понимает |
|---|---|
| `exit-code` | только код возврата (по умолчанию) |
| `jest` | строки `PASS`/`FAIL <файл>`, итоги `Tests:`, имена упавших после `●` |
| `vitest` | `✓`/`×`/`❯ … failed`/`FAIL <файл>`, итоги `Test Files`/`Tests` |
| `go-test` | `ok <пакет>` / `FAIL <пакет>`, имена из `--- FAIL:` |
| `pytest` | `-v` и короткий вывод, итоговая строка `=== … passed/failed ===` |

Только у `jest` и `pytest` с вводом (`{input}` в команде) диспетчерская умеет сама строить ввод «прогнать вот эти спеки» — для перепрогона упавших и узкого регресса. У остальных заготовок и у своих регулярок этого нет.

## Свои регулярки

Вместо имени — объект из четырёх регулярок. Пусть раннер проекта печатает так:

```
ok   apps/api/orders.test.mjs (1.2 s)
FAIL apps/api/cart.test.mjs
  ✗ пустая корзина не оформляется
summary: 41 passed, 1 failed
```

Тогда задача (строки JSON: обратная косая черта удваивается):

```json
"tasks": {
  "api-test": {
    "label": "API: тесты", "run": "npx demo-runner {input}", "input": { "label": "файлы" },
    "parser": {
      "pass":   "^ok\\s+(\\S+)",
      "fail":   "^FAIL\\s+(\\S+)",
      "totals": "^summary:",
      "names":  "^\\s+✗\\s+(.+)$"
    }
  }
}
```

- `pass`, `fail` — строка спеки; **группа 1 обязательна** — имя спеки. Проверка конфига отказывает, если группы нет.
- `totals` — строки итога целиком (на страницу идут последние четыре).
- `names` — имя упавшего теста (группа 1, если есть; иначе вся совпавшая часть); показывается до 25 имён.
- Нужна хотя бы одна из `pass`, `fail`, `totals`. Других ключей нет.

Как читается вывод: построчно, цвета ANSI вырезаются. Строка сначала проверяется на `fail`, и только если не совпала — на `pass`. Спека, упавшая хоть раз, в прошедшие не попадает.

## Функция `parseOutput`

Если вывод не разобрать построчными регулярками (JSON-отчёт, многострочные блоки), разбор пишется функцией в `dispatcher.project.mjs`:

```js
// dispatcher.project.mjs
export function parseOutput(text, taskId) {
  if (taskId !== "e2e") return null // остальным задачам — их `parser` из конфига
  const passed = [], failed = []
  for (const line of text.split("\n")) {
    const m = /^\s*(PASSED|FAILED)\s+(\S+)/.exec(line)
    if (m) (m[1] === "PASSED" ? passed : failed).push(m[2])
  }
  return { passed, failed, totals: [], names: [] }
}
```

Функция получает весь вывод прогона и id задачи, возвращает `{ passed, failed, totals, names }` (списки строк) или `null` — тогда работает `parser` задачи. Исключение в функции не роняет сервер: пишется в журнал, и берётся `parser`.

## Подводные камни

- Пока функция `parseOutput` есть, диспетчерская считает, что имена спек знает **любая** задача, даже `exit-code`. Для задач, которые разбирать не надо, функция всё равно должна вернуть честный результат: пустые списки у красного прогона читаются как «упало неизвестно что».
- Имя спеки из `pass` и `fail` должно совпадать с тем, как спека названа в дереве (путь или имя файла): по нему регресс ищет соседей тронутых файлов.
- Раннер, который печатает итог только в конце, но падает раньше (таймаут, OOM), даст пустые списки — красный прогон без имён. Это нормально, но выжимки не будет.
- Двойные косые черты в JSON: `"\\s"` в файле — это `\s` в регулярке.
- Заготовки — `scripts/dev/dashboard/parsers.mjs`; там же видно, как регулярки применяются.
