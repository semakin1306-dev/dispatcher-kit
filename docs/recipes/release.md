# Выкат стенда и прода, проверка после выката

## Когда нужно

Модуль `release` даёт на странице две кнопки: «Выкатить стенд» (интеграционная ветка → тестовый стенд) и «Выкат в прод» (влив `staging → main` и пуш прод-ветки). Обе — только руками человека: ни автономия, ни ответ из Телеграма их не нажимают.

## Конфиг

```json
"modules": { "release": true },
"repo": { "main": "~/code/demo-shop", "upstream": { "staging": "develop", "main": "main" } },
"release": {
  "stand": { "run": "./scripts/deploy-stand.sh", "url": "https://stand.example.com" },
  "prod":  { "run": "./scripts/deploy-prod.sh", "verify": "./scripts/smoke-prod.sh", "pushDeploys": false }
}
```

| Ключ | Что значит |
|---|---|
| `release.stand.run` | команда выката стенда |
| `release.stand.url` | адрес стенда: показывается на странице, уходит приёмке |
| `release.prod.run` | команда выката прода после пуша прод-ветки; пусто — команды нет |
| `release.prod.verify` | проверка после выката прода; ненулевой код красит выкат |
| `release.prod.pushDeploys` | пуш в прод-ветку **сам** выкатывает прод (через CI) |

Модуль включается, когда задан хотя бы один из `release.stand.run`, `release.prod.run`, `release.prod.pushDeploys`. Выкат прода требует прод-ветку: при `repo.upstream.main: null` раздел `release.prod` — ошибка конфига.

## Выкат стенда

1. Проверки перед выкатом: основная папка проекта стоит на `staging` и без изменений отслеживаемых файлов; команда задана; гарды зелёные на дереве `staging` (рекомендация, не запрет).
2. `git push <remote> staging:<интеграционная ветка>`.
3. `release.stand.run` в основной папке проекта.

После выката диспетчерская сама просит у агентов чек-листы приёмки (если включён модуль `accept`).

Отдельного ключа проверки стенда нет: проверку допишите в конец команды (`./scripts/deploy-stand.sh && ./scripts/smoke-stand.sh`) или задачей проекта, которую агент назовёт в напоминании `ПОСЛЕ ВЫКАТА` (см. [приёмка](stand-acceptance.md)).

## Выкат прода и папка `_main`

Влив `staging → main` идёт не в основной папке проекта (она остаётся на `staging`), а в отдельной рабочей копии на ветке `main` — `<папка слотов>/_main`. Её создаёт человек один раз:

```
git -C ~/code/demo-shop worktree add ~/code/demo-shop-wt/_main main
```

Проверки перед выкатом: папка есть, стоит на `main` и чистая; `main` — предок `staging` (иначе в прод-ветку попало что-то мимо `staging`); в `staging` есть что выкатывать; гарды зелёные; прод-ветка на remote не ушла вперёд; при модуле `accept` — сколько волн принято.

Шаги:

1. `git fetch`; ещё раз проверить, что прод-ветка remote и `main` — предки `staging`.
2. `git merge --no-ff staging` в `_main`; убедиться, что дерево `main` совпало с деревом `staging`.
3. `git push <remote> main:<прод-ветка>` (обрыв связи — несколько попыток со сверкой, дошёл ли пуш).
4. `release.prod.run`, затем `release.prod.verify` — в папке `_main`.

## Пуш, который сам выкатывает

Если CI проекта выкатывает прод по пушу в прод-ветку, поставьте `pushDeploys: true` и обычно оставьте `prod.run` пустым. Тогда диспетчерская называет пуш выкатом во всех текстах и проверках. `verify` всё равно выполнится сразу после пуша — если CI выкатывает долго, проверка должна сама ждать (например, опрашивать версию на сайте до совпадения с коммитом, с пределом по времени).

## Подводные камни

- Команды выката идут строкой в оболочку на этой машине. Секреты выката держите там, где их ждёт ваш скрипт (агент слота их не видит: ssh, `.env` и пуш ему закрыты).
- Защитите скрипты выката от правки агентами: `protected` (например `["deploy*.sh", "scripts/deploy-*"]`) и `deny.edit` для файлов CI.
- `verify` должен проверять то, что видит пользователь (ответ страницы, версия сборки), а не «процесс запущен».
- Прод-ветка ушла вперёд `staging` (горячая правка мимо диспетчерской) — выкат откажет. Сначала влейте её в `staging`.
