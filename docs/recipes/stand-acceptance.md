# Приёмка на стенде

## Когда нужна

Волна влита в `staging` и выкачена на тестовый стенд. Тесты проверили код, но не то, что видит пользователь. Модуль `accept` собирает с агента волны чек-лист приёмки, гоняет по нему тесты против стенда и даёт человеку поставить вердикт.

## Конфиг

```json
"modules": { "release": true, "accept": true },
"release": { "stand": { "run": "./scripts/deploy-stand.sh", "url": "https://stand.example.com" } },
"accept": {
  "run": "node scripts/accept.mjs",
  "specGlob": "e2e/accept/**/*.spec.ts",
  "standUrl": "https://stand.example.com"
}
```

- `accept.run` — команда прогона приёмки; без неё модуль не включится. Идёт в основной папке проекта, строкой в оболочку.
- `accept.standUrl` — адрес стенда для команды и для ссылок «где» в чек-листе; не задан — берётся `release.stand.url`.
- `accept.specGlob` — где лежат спеки приёмки (путь от корня репозитория). Спека волны — файл под этим шаблоном, в пути которого есть номер волны: `wv-0042` или `wv0042`. Квиз этот ключ не спрашивает — допишите руками.

## Чек-лист: пять полей

После выката на стенд диспетчерская просит у агента каждой волны чек-лист — один блок кода с языком `checklist`, пункт на строку, пять полей через ` | `:

```checklist
- i1 | /cart | добавить товар и открыть корзину | товар в корзине, сумма пересчитана | авто
- i2 | /cart | оформить пустую корзину | кнопка неактивна, подсказка видна | авто
- i3 | письмо клиенту | оформить заказ | письмо пришло, ссылка ведёт в заказ | руками
```

- `iN` — номер пункта (`i1`, `i2`, подпункт — `i1b`);
- где — адрес экрана (путь откроется на стенде ссылкой) или место;
- что сделать; что должно получиться;
- `авто` — пункт проверяет тест, `руками` — человек.

Строки, которые не разобрались, показываются списком; ответ без годных пунктов не принимается.

## Метки `[iN]` в тестах

Тест для пункта «авто» называется с метки пункта: `[i1] товар в корзине, сумма пересчитана`. Диспетчерская ищет метки в выводе команды приёмки и ставит на пункты «авто ✓/✗». Понимает отметки Playwright, jest, vitest, pytest и go. Волна строки определяется по номеру волны в строке (в имени файла спеки); если волна в прогоне одна — все строки её. Пункт без спеки агент может написать сам: кнопка «заказать спеку».

## Окружение команды

| Переменная | Что в ней |
|---|---|
| `DISPATCHER_STAND_URL` | адрес стенда |
| `DISPATCHER_ACCEPT_WAVES` | волны прогона через пробел, `WV-0042 WV-0043` |
| `DISPATCHER_ACCEPT_SPEC` | файлы спек этих волн через пробел (только если задан `specGlob`) |
| `DISPATCHER_ACCEPT_ITEMS` | при перепрогоне части пунктов — регулярка меток `\[i1\]\|\[i3\]` для `--grep`, `-t`, `-k` |

Команда идёт строкой в оболочку, а на Windows это `cmd.exe`, где `$ПЕРЕМЕННАЯ` не раскрывается. Поэтому надёжнее короткий скрипт в проекте, который сам читает переменные и собирает вызов раннера: пустой `DISPATCHER_ACCEPT_ITEMS` — без фильтра, непустой — `--grep`.

Если `specGlob` задан, а у ждущих волн спек нет, прогон отказывается сразу.

## Вердикт

Вердикт «принято / не принято» ставит только человек; итоги уходят агентам волн и оркестратору кнопкой «Отправить итоги». Новый влив волны с кодом продукта снимает вердикт «на разбор»; влив только тестов и документов приёмку не трогает. Волна, ни один влив которой не трогал код продукта, принимается сама — человек может перевернуть вердикт.

Агент волны может оставить напоминание строкой `ПОСЛЕ ВЫКАТА: что сделать :: <id задачи>` — на странице появится карточка, а кнопка на ней запустит задачу проекта без ввода с `DISPATCHER_STAND_URL`. Любая другая команда после `::` показывается только текстом.

## Тестовые персоны

Если у продукта есть роли (покупатель, продавец, администратор), приёмка проверяет пункты от лица разных пользователей. В ядре персон нет; организовать их у себя можно так:

- **Набор постоянных пользователей стенда**, по одному на роль. Создаёт их идемпотентный скрипт заполнения стенда, который идёт после выката (частью `release.stand.run`): повторный запуск ничего не ломает.
- **Пароли и ключи — вне git.** В хранилище секретов CI или в переменных окружения машины, где идёт приёмка; скрипт приёмки читает их сам. В чек-листе и в выводе тестов — только роль, без данных входа.
- **Роль — в поле «где» или в тексте пункта**: «/orders (продавец)». Отдельного поля роли в чек-листе нет.
- **Вход в тестах — через API или сохранённое состояние сессии**, а не формой на каждом тесте. Если вход идёт формой, не печатайте в лог адрес страницы после отправки: форма до загрузки скриптов может уйти обычным GET, и пароль окажется в строке запроса.
- **Данные пункта — свои.** Каждый `[iN]` создаёт себе нужное сам и проходит отдельно от соседей: перепрогон одного пункта не должен зависеть от того, что сделал предыдущий.

## Подводные камни

- Модуль `accept` работает и без модуля `release`, но тогда нет станции «На стенде», а чек-листы сами не просятся: сами они просятся после выката стенда из диспетчерской, иначе — кнопкой «Опросить ветки».
- Спека находится по номеру волны в пути: `e2e/accept/wv-0042-cart.spec.ts` — да, `e2e/accept/cart.spec.ts` — нет.
- Команда приёмки идёт в основной папке проекта и видит тот код, на котором эта папка стоит. Спеки, которых ещё нет в основной папке (не влиты), прогон не найдёт.
