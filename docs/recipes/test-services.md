# Службы для тестов: БД, Redis, очередь

## Когда нужно

Интеграционным тестам нужна живая база, кэш или очередь. Диспетчерская умеет поднимать их перед прогоном и проверять, что они живы.

## Ключ

У каждой машины в `machines` — список служб:

```json
"machines": {
  "build": {
    "ssh": "build-box", "dir": "~/dk/demo-shop", "workers": 2,
    "services": [
      {
        "name": "postgres",
        "up":    "docker compose -p demo-shop-tests -f compose.test.yml up -d postgres",
        "check": "docker compose -p demo-shop-tests -f compose.test.yml exec -T postgres pg_isready -q",
        "down":  "docker compose -p demo-shop-tests -f compose.test.yml down"
      }
    ]
  }
}
```

`name` и `up` обязательны, `check` и `down` — нет.

## Как это работает

Порядок один для всех машин — и для этой, и для удалённых (код один: `scripts/dev/dashboard/services.mjs`). Перед прогоном, которому нужны службы:

1. если у службы есть `check` и он проходит — служба уже работает, `up` не запускается;
2. иначе — `up`, затем `check` до 15 раз с паузой 2 с; не ответила — прогон красный со строкой «✗ служба … не отвечает после запуска», команды прогона не запускаются;
3. без `check` служба запускается через `up` при каждом прогоне;
4. `down` — после прогона, если на машине не осталось других прогонов, которым нужны службы. Не нужно останавливать — не задавайте `down`.

Службы нужны прогонам задач проекта (`tasks`) и поезду, когда он гоняет проверки на этой машине. Служебным прогонам (влив, коммит, ревью, подготовка папки) — нет.

Каждая команда идёт отдельным `bash -ec`, без ввода. На Windows это Git Bash (как и у задач с вводом через пускатель `.cmd`); не найден — прогон красный с подсказкой поставить Git for Windows или задать `DISPATCHER_BASH`.

**На этой машине** (`machines.local.services`) службы поднимает ядро диспетчерской: модуль `machines` для этого не нужен. Команды выполняются в папке слота (у прогонов staging и поезда — в основной папке проекта). Подъёмы и остановки идут по одному: второй прогон ждёт первый и видит уже поднятую службу. Кроме того, монитор раз в 15 с выполняет `check` тем же способом и показывает итог. Стартовая настройка кладёт ответ о службах сюда.

**На удалённой машине** (модуль `machines`) службы поднимаются в папке прогона — то есть с кодом того же коммита, что и тесты; команды уходят в общем скрипте прогона по ssh.

Переменные в командах служб:

| Где | Переменные |
|---|---|
| эта машина: `up`, `check`, `down` | `DISPATCHER_MACHINE=local`, `DISPATCHER_SLOT`, `DISPATCHER_JOB` (у `down` — последнего прогона) |
| удалённая машина: `up`, `check` | `DISPATCHER_MACHINE`, `DISPATCHER_PLACE` (номер места, от 0), `DISPATCHER_SLOT`, `DISPATCHER_JOB` |
| удалённая машина: `down` | без переменных `DISPATCHER_*` |

Если прогоны идут на удалённой машине, перенесите службы в её запись.

## docker compose: имя проекта

Задавайте имя проекта compose явно — ключом `-p`. Без него compose берёт имя папки, а папка прогона называется по слоту и месту (`<слот>-p<место>`): у двух проектов на одной машине имена совпадут, и их контейнеры перемешаются.

Два варианта:

- **Одна связка служб на машину.** Постоянное имя (`-p demo-shop-tests`), как в примере выше. `down` работает надёжно. Параллельные прогоны на одной машине делят одну базу — тесты должны изолироваться сами, например отдельной базой на место: имя базы из `DISPATCHER_PLACE`.
- **Своя связка на каждое место прогона.** Имя из папки прогона: `-p "demo-shop-$(basename "$PWD")"`, и порты тоже по месту (через `DISPATCHER_PLACE` в файле compose или переменных). Учтите: `down` выполняется в папке последнего прогона и **без** переменных `DISPATCHER_*` — поэтому имя должно выводиться из `$PWD`, а не из переменных. Связки остальных мест остаются запущенными и переиспользуются следующими прогонами (их `check` пройдёт).

## Подводные камни

- `check` должен быть быстрым и честным: код 0 — служба принимает соединения, а не «контейнер существует». `pg_isready`, `redis-cli ping`, проверка порта.
- `up` должен возвращаться, когда служба запущена в фоне (`up -d`), а не держать терминал.
- Все команды — `bash -ec`: первая упавшая команда внутри строки останавливает её.
- Если тестам нужна схема базы, миграции — часть `up` или отдельный шаг `prepare` машины, а не теста.
